# 詳細

目標：リポジトリごとに `.actrc` を手作業で調整することなく、このリポジトリのすべてのワークフローを `act` で正しく、かつ最小限のコンテナの重さで実行できるようにせよ。

## 1. ワークフローの棚卸し

- すべての `.github/workflows/*.yml`（または `.yaml`）を列挙せよ。
- ジョブごとに次を記録せよ：`runs-on` の値、すべての `uses:` アクション、Dockerを呼び出すかどうか（`docker build`、`docker run`、`services:` ブロック、`uses: docker://...`）、および `${{ secrets.* }}` / `${{ env.* }}` の参照。
- すでに存在する `if: ${{ env.ACT }}` 条件に注意せよ — これらは既存のact専用の配慮なので、維持せよ。

## 2. ランナーイメージの選定

異なる `runs-on` の値それぞれを、`-P` フラグで `catthehacker/ubuntu` のイメージタグに対応付けよ：

- `ubuntu-latest`、`ubuntu-24.04`、`ubuntu-slim` など → `catthehacker/ubuntu:act-24.04`（または対応するUbuntuバージョン）。`-slim` タグは、ワークフローがNode/bash以上のものを必要としない場合のみ使え — `setup-*` アクション（bun、biome、node）を使うワークフローの大半は、自身をインストールする必要がある場合があるため、フルの `act-24.04` タグが必要になる。
- ジョブが `docker build`/`docker run` を実行するだけで自前でツールをインストールしないなら、`act-24.04` で問題ない。ユーザーの明示的な指示でジョブを実行し、引き続きパスすることを確認しない限り、`micro` にダウングレードするな。
- セルフホストまたはUbuntu以外の `runs-on` の値は、出力に手動の注記が必要 — actはそれらをエミュレートできないので、イメージを推測せず、フラグを立てて指摘せよ。

## 3. Docker-in-Dockerジョブの扱い

いずれかのジョブがDockerイメージをビルドまたは実行する場合：

- そのジョブに `docker.io`（または同等のもの）をインストールする `if: ${{ env.ACT }}` ステップがすでにあるか確認せよ — なければ、リポジトリ内の他のワークフローに同様のステップがあればそのパターンに合わせ、なければ最小限のステップを新規に追加せよ。
- `.actrc` には動作するDockerソケットが必要。WindowsでDocker Desktopの場合は通常 `--container-daemon-socket -`（自動）で動作する。Podman machineの場合は `--container-daemon-socket npipe:////./pipe/<machine-name>`。Linux/macOSではデフォルトの `/var/run/docker.sock` で上書き不要 — デフォルトで解決できない場合にのみ `--container-daemon-socket` を追加せよ。

## 4. 必要に応じてシークレット/環境変数の雛形を作成

いずれかのワークフローが `${{ secrets.X }}` を参照している場合：

- `.secrets` 自体は作成するな。代わりに、必要な各キーを空/プレースホルダーの値にした `.secrets.example` を作成し、`.gitignore` に `.secrets` がまだなければ追加せよ。
- `.actrc` に `--secret-file .secrets` を追加するのは、`.secrets` がローカルに存在すると見込まれる場合のみとせよ。そうでなければ、ユーザーが実行ごとに `-s KEY=value` で渡すよう任せよ。

## 5. `.actrc` の作成

手順1で見つかった異なる `runs-on` の値ごとに `-P runner=image` の行を1行ずつ書き、必要なら手順3のデーモンソケットの行を加えよ。ワークフローに存在しない懸念に対するフラグは追加するな（シークレットを何も使っていなければ `--secret-file` は不要、使われていないランナーのための余分な `-P` エントリーも不要）。

## 6. タスクランナーのショートカットを追加（言語を問わない — package.json/Makefile/justfile/composer.json/pyproject.tomlなどを持つあらゆるプロジェクト）

ジョブ名ごとに、`act -j <job-name>` に相当する便利スクリプトを、リポジトリですでに使われているタスクランナーの慣例（`npm`/`bun` のスクリプト、`Makefile` のターゲットなど）に従って追加せよ。さらに、既存の命名に合わせて、ジョブを一覧表示する（`act -l`）か全ジョブを実行する、素の `act` スクリプトも追加せよ。タスクランナーが存在しない場合は新規作成せず、スキップした旨を報告せよ。

## 7. 検証

以下の `act` コマンドは、ユーザーに明示的に指示された場合のみ順番に実行し、失敗は推測で黙って修正せずに報告せよ。指示がなければ実行せず、コマンドを提示するにとどめよ：

```
act -l
act -n                      # ドライラン、全ジョブ
act -j <job> --dryrun       # -n の出力が多すぎる場合はジョブごとに
```

Dockerに依存するジョブでは、ドライランではデーモンソケットの問題を検出できない — その旨をユーザーに伝え、明示的に指示された場合のみ実際にジョブを実行し（`act -j <job>`）、Dockerのステップまで到達することを確認せよ。

## 出力

以下を報告せよ：`.actrc` の差分、新しい `.secrets.example`/`.gitignore` のエントリー、ワークフローの差分（手順3で変更した場合）、タスクランナーのショートカットの差分、および検証コマンドの結果（未実行の場合はその旨と提示したコマンド）。`act` でエミュレートできない `runs-on` があれば、（黙ってスキップせず）フラグを立てて指摘せよ。
